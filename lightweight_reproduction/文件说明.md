我已经把你仓库当前 `main` 分支里的 `lightweight_reproduction` 读了一遍。这个文件夹其实可以用一句话概括：

> 它做的不是“训练/运行 HUGE-Bench 的 VLA 模型”，而是对 HUGE-Bench 官方公开的轨迹阶段标注做一次完整的、本地 CPU 可运行的“数据复现 + 完整性验证 + 统计分析 + 可视化报告”。

## 1. 先建立一个最重要的整体认识

整个程序实际上就是下面这条流水线：

```text
HUGE-Bench 官方阶段标注
        ↓
     loader.py
   读取 JSON/JSONL
        ↓
     models.py

        ↓
   validation.py
```

# 2. 你首先必须理解两个概念：Episode 和 Stage

这基本是理解整个 `lightweight_reproduction` 的钥匙。

### Episode 是什么？

你可以把一个 Episode 理解为：

> “无人机完成一条完整高级任务的一次完整轨迹样本。”

例如指令：

```text
飞向建筑物 → 绕建筑一周 → 最后降落
```

假设整个过程有 600 帧。

那么这就是：

```text
1 Episode
length = 600 frames
```

在 `models.py` 中，`EpisodeRecord` 保存：

```text
episode_index
task_id
env_id
traj_id
length
instruction
num_stages
annotation_provenance
...
```

也就是说，它描述的是“一整条任务轨迹”。

------

### Stage 又是什么？

HUGE-Bench 的关键就在这里。

一个高级任务不是一个动作，而是多个阶段组成。

例如：

```text
完整 Episode
│
├── Stage 1：飞向建筑物
├── Stage 2：绕建筑物飞行
└── Stage 3：降落
```

如果有 600 帧：

```text
Stage 1     0 ~ 149
Stage 2   150 ~ 449
Stage 3   450 ~ 599
```

每一个 Stage 在 `StageRecord` 中记录：

```text
task_id
subtask_id
frame_start
frame_end
subtask_text
...
```

并且程序定义：

```python
duration_frames = frame_end - frame_start + 1
duration_seconds = duration_frames / 5
```

因为这里按照 5 FPS 计算。

所以：

> Episode = 一条完整高级任务轨迹
> Stage = 这条轨迹里面的某一个子任务阶段

而你的轻量复现，核心就是在分析这两个层次。

# 3. `models.py`：定义“数据长什么样”

这个文件非常简单，但非常重要。

它没有算法，主要定义 Python 的 `dataclass`。

核心结构是：

```text
AnnotationDataset
│
├── AnnotationManifest
│
├── episodes_by_split
│      ├── train
│      ├── test_seen
│      └── test_unseen
│
└── stages_by_split
       ├── train
       ├── test_seen
       └── test_unseen
```

其中：

```python
EpisodeRecord
```

是一条完整任务轨迹。

```python
StageRecord
```

是一段子任务。

```python
AnnotationManifest
```

是整个数据集的“目录和身份证”，记录：

- 数据版本
- 数据来源
- 8 个任务
- train/test_seen/test_unseen 数量
- 总 episode 数量
- 总 stage 数量
- 文件大小
- SHA256

你可以把 `models.py` 理解成：

> “规定后面的程序统一使用什么数据格式。”

# 4. `loader.py`：把硬盘上的标注读进 Python

这是第二个建议你认真看的文件。

它读取的不是图像，不是模型权重，而是类似：

```text
manifest.json

episode_mapping/
├── train.jsonl
├── test_seen.jsonl
└── test_unseen.jsonl

stage_segments/
├── train.jsonl
├── test_seen.jsonl
└── test_unseen.jsonl
```

`load_annotations()` 的核心逻辑非常直白：

```python
manifest = load_manifest(root)

for split in:
    train
    test_seen
    test_unseen

    读取 episode_mapping
    读取 stage_segments
```

然后：

```text
JSON
 ↓
dict
 ↓
EpisodeRecord / StageRecord
 ↓
AnnotationDataset
```

这里使用 JSONL，而不是普通 JSON。

例如：

```json
{"episode_index":0,"task_id":"road",...}
{"episode_index":1,"task_id":"orbit",...}
{"episode_index":2,"task_id":"farm",...}
```

一行就是一个样本。

这样一个好处是不用一次把超大的 JSON 全读到内存里。代码里的 `iter_jsonl()` 就是一行一行读取。

# 5. `validation.py`：整个项目最有“复现价值”的部分之一

这个文件做的事情就是：

> “证明你读取的数据确实与官方发布的数据一致，而且内部逻辑没有问题。”

这里验证得非常严格。

例如官方数量直接写进了程序：

```python
train        = 5175 episodes
test_seen    = 576
test_unseen  = 417

总计 = 6168
```

Stage：

```text
train        23115
test_seen     2573
test_unseen   1851

总计         27539
```

它大致检查五层东西。

第一层是“文件对不对”：

```text
文件是否存在
文件大小是否一致
SHA-256 是否一致
```

甚至考虑到了 Windows：

```text
LF
CRLF
```

换行符差异的问题。

第二层是“数据规模对不对”：

```text
train episode 数量
test_seen episode 数量
test_unseen episode 数量

stage 数量
总 episode 数量
总 stage 数量
```

第三层是“Episode 自己是否合法”：

例如：

```text
length > 0
num_stages > 0
task_id 属于官方八个任务
env_id 不是空字符串
instruction 不是空字符串
```

第四层是“Stage 与 Episode 是否匹配”。

比如一个 Episode：

```text
length = 600
num_stages = 3
```

程序要求：

```text
确实存在 3 个 stage
```

同时：

```text
0 <= frame_start <= frame_end < 600
```

第五层，也是非常关键的：

### Stage 是否连续覆盖整个 Episode

比如正确的是：

```text
Stage 1:   0 ─── 149
Stage 2: 150 ─── 449
Stage 3: 450 ─── 599
```

程序要求：

```python
current.frame_start == previous.frame_end + 1
```

既不能：

```text
149 → 160
```

出现 gap；

也不能：

```text
149 → 140
```

出现 overlap。

最终最后一个 Stage 还必须正好结束在：

```python
episode.length - 1
```

所以这一块其实在证明：

> HUGE-Bench 的阶段标注确实能够完整地把一条高级任务轨迹划分成连续的子任务阶段。

这和 HUGE-Bench 论文里的“process-oriented / multi-stage”思想是高度相关的。

# 6. `analysis.py`：开始真正做统计分析

验证通过以后，才进入这个模块。

它定义了 8 个任务 ID：

```python

 "road", "farm", "obstacle", "orbit_multi")
```

主要计算四类东西。

### 数据集整体统计

生成：

```text
dataset_overview.csv
```

包括：

```text
episodes
episode_percent
total_frames
total_hours_at_5fps
stage_segments
mean_episode_frames
median_episode_frames
mean_stages_per_episode
unique_tasks
unique_scenes
```

------

### 每个任务的统计

生成：

```text
task_statistics.csv
```

相当于回答：

```text
Landing 有多少轨迹？
Orbit 有多少？
Road 有多少？

每种任务平均多长？
平均几个阶段？

```

------

### Task × Scene 统计

生成：

```text
task_scene_matrix.csv
```

本质是一个矩阵：

```text
                  Scene A  Scene B  Scene C ...
Landing              100      200       0
```

------

### Stage 统计

生成：

```text

```

```text
task_id + subtask_id
```

```text

平均持续帧数
中位数
P25
P75
秒数
不同 subtask 文本数量
```

所以 `analysis.py` 可以理解成：

> validation.py 问“数据对不对”；analysis.py 问“这些数据有什么统计特征”。

# 7. `metric_smoke.py`：千万别误解这个文件

这个特别容易被误解成：

> “复现论文指标。”

实际上完全不是。

它自己甚至写得非常明确：

```text
Synthetic metric implementation smoke test
— not a paper result.
```

它做的只是创建一条极简单的假轨迹：

```python
[0, 0, 0]
[1, 0, 0]
[2, 0, 0]
```

然后：

```python
GT   = 这条轨迹
Pred = 同一条轨迹
```

再调用 HUGE-Bench 官方的：

```python
compute_avg_tcr()
compute_ndtw()
compute_nsp()
compute_success()
path_length_xyz()
```

目的只是：

> “看看官方 `metric.py` 在你这个 Python 环境里能不能正常 import、调用、返回有限数值。”

不是拿 π0：

```text
Image → Model → Predicted trajectory
```

再和 GT 比。

所以它只是：

```text
metric.py API compatibility test
```

不是论文实验复现。

这点你汇报时一定要说清楚。


对应含义非常直观：

| 图   | 含义                           |
| ---- | ------------------------------ |
| 01   | Train / Seen / Unseen 数据规模 |
| 02   | 8 类任务的数据量               |
| 03   | 8 类任务 × 场景覆盖情况        |
| 04   | 每条轨迹有多长                 |

```text

```

> 高级任务 → 多阶段过程

代码还会针对每种任务选一个“接近该任务轨迹长度中位数”的代表 Episode，再把它里面的 Stage 画成时间线。这个 representative episode 的选择逻辑在 `analysis.py` 里。

`plots.py` 使用 matplotlib 的无界面 `Agg` 后端，因此服务器、CPU 环境都可以直接出图，并固定以 180 DPI 保存。


这个设计其实比较规范：

```text

```

这样避免 Markdown 和 HTML 两份报告中的统计结果不一致。

## 17. 如果你现在要真正“读懂代码”，我建议按这个顺序

```text
       ↓
```
